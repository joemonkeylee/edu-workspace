# 文本层实测结论 + 开工前遗留问题

> 分支 `feature/pdf-native`，尚无代码改动。本轮为全量实测，非抽样。

---

## 一、文本层是什么

PDF 页面内部有两种完全不同的内容载体：

| | 矢量文本 PDF | 扫描图像 PDF |
|---|---|---|
| 页面内容 | 字符编码 + 字体引用 + 位置坐标 | 整页一张位图 |
| 产生方式 | Word / 排版软件导出 | 扫描仪、图片转 PDF |
| `getTextContent()` | 返回带坐标的文字项 | 返回空 |
| 搜索 | 直接建索引，零成本 | 必须先 OCR |

判断方法就是调 `page.getTextContent()`，看有没有拿到东西 —— 但**"拿到了"不等于"能搜"**，还有一层假阳性（见 §三）。

## 二、全量实测结果（5661 本，253 秒，0 解析失败）

每本抽首 / 中 / 尾 3 页，累计统计。

| 分类 | 本数 | 占比 | 页数 | 页数占比 |
|---|---|---|---|---|
| **可搜** | **5480** | **96.8%** | 96025 | 91.6% |
| 无文本层（扫描件） | 174 | 3.1% | 8370 | 8.0% |
| 真乱码（编码映射失败） | 2 | 0.04% | 300 | 0.3% |
| 只有水印串 | 5 | 0.1% | 83 | 0.1% |

```
不可搜合计：181 本 / 8753 页 = 3.2% 的书、8.4% 的页
可搜本平均 17.5 页，不可搜本平均 48.4 页
（扫描件普遍是厚书，所以按页数口径占比更高）
```

**结论：搜索对 96.8% 的书可用，是真实红利，不是画饼。**

## 三、判定规则（踩了两个坑才定下来）

导入时每本抽 3 页，按下列顺序判：

```
1. 累计去空白字符 < 20        → no_text        扫描件，不可搜
2. 控制字符占比 > 2%          → garbled        编码映射失败，不可搜
3. 长度 < 300 且无中日韩字符  → watermark_only 只有水印串，不可搜
4. 其余                       → ok             可搜
```

**踩过的坑（重要，别再犯）：**

- ❌ **不能用"私用区字符占比"判乱码。** 数学公式字体（MathType / KaTeX 类）大量用 U+E000–F8FF 编码符号。
  实测 priv 占比 10~21% 的 34 本，抽看全部是可读中文（如 `3.1等量关系和方程题型一方程的概念`），误判率 100%。
- ❌ **不能用"可打印字符占比"判乱码。** 中文全角标点（、。（）．×÷①②③）不在常见 printable 区间里，正常书也会被算成 0.62。
- ❌ **不能用"CJK 占比低"判乱码。** 英语试卷 CJK 只有 3~5%（`七年级英语Unit1测试试卷`），但完全可读可搜。
- ✅ **控制字符占比是真信号。** 两本真乱码分别是 `ctrl=0.60` 和 `ctrl=0.97`，特征极其明确。

### 边界情况

- **部分页无文本**：48 本存在"抽样的 3 页里有几页没文字"（封面是图、正文有字，很正常）。
  → 判定必须按**整本累计**，不能单页一票否决。
- **只有水印**：`{#{QQABYYQAgggAABAAAQhCAwVgCAOQkhACAagGQAAIsAAASAFABAA=}#}` 是学科网的数字指纹串，
  174 个字符全是它，没有任何正文 → 不可搜。

## 四、搜索必须要文本层吗

**是，100% 必须。** 只有两条路：

1. 有文本层 → 提取 → 存 `pdf_page_text` → 直接搜
2. 无文本层 → 必须先 OCR（tesseract 一类）→ 中文准确率一般、耗时长、结果要另存一份

一期建议：**只做第 1 条**。181 本不可搜的书不做 OCR，标记后 UI 隐藏搜索入口即可，其余功能（渲染、批注、作业、错题）完全不受影响。

### 字段调整

原计划里的 `hasTextLayer Boolean` 不够用，改成：

```prisma
/// ok = 可搜索；no_text = 扫描件；garbled = 编码损坏；watermark_only = 只有水印
searchable  String  @default("ok") @db.VarChar(16)
textStats   Json?   // { sampledPages, avgCharsPerPage, ctrlRatio } 便于复查
```

## 五、开工前的遗留问题（需要你拍板）

### A. 中文搜索怎么索引 ⚠️ 最重要的一个

MySQL 的 `FULLTEXT` **默认不分词中文**（内置 parser 按空格/标点切，中文整段是一个 token）。

| 方案 | 做法 | 代价 |
|---|---|---|
| **1（建议一期）** | 单本内 `LIKE '%关键词%'`，扫描该书 17.5 行的 `plainText` | 毫秒级，零配置 |
| 2 | 跨全库 `LIKE`：96025 行全表扫 | 预估 1~3 秒，能接受但不优雅 |
| 3 | `FULLTEXT ... WITH PARSER ngram`（需 `ngram_token_size=2`） | 要改 MySQL 配置，跨库秒级 |

**我建议一期只做方案 1**（在书内搜），跨全库搜索二期再说。理由：真实场景大概率是"在这本练习册里找某道题"，而单本搜索既快又零配置。

数据量估算：96025 页 × 约 500 字/页 ≈ 4800 万字 ≈ 144 MB，存 MySQL 毫无压力。

### B. 缩略图到底生成多少

你说"导入时切一张就行"。但如果只做封面，**页缩略图 tab（几十~几百页）是唯一的性能风险点**。两个选择：

| 方案 | 存储 | 代价 |
|---|---|---|
| 只做封面 | 5661 × ~20KB(200px) ≈ **113 MB** | 页缩略图 tab 要前端懒渲染 + 虚拟化，有卡顿风险 |
| 封面 + 全页缩略图（100px 约 5KB/页） | 113 MB + 96025 × 5KB ≈ **593 MB** | tab 零卡顿，前端最简单 |

**我建议第二种。** 593 MB 对比现在的 82.6 GB PNG 完全不值一提，换来的是彻底消灭唯一的性能风险点，而且导入时反正要抽文本，顺手渲染即可。

### C. 页面尺寸按页存

上一轮只抽了 60 本验证"同书内页面尺寸一致"，**没有全量验证**。
建议 `pdf_page_text` / 尺寸快照按**每页**存 `pageSizePt`，而不是只存第一页。成本几乎为零，但即使遇到混排的书也不会错位。

### D. 作业导出

现在服务端只返回 PNG 路径 + 笔迹，前端合成（`assignments.ts:327`）。
PDF 模式：前端用 pdf.js 渲染该页 + 叠笔迹 → `canvas.toBlob()` 出图 → 上传。
**如果要导出成图片，零新依赖**；只有要导出成 PDF 才需要引入 `pdf-lib`。

### E. 迁移兜底（你第 2 点的补充）

已验证：`Book.fileHash` 是 `sha256(pdf文件)`（`pdfProcessor.ts:352`），14665 本**全部有值、14665 个唯一、0 重复** —— 拿来当关联键完全成立。

但建议加兜底：将来扫盘时若 PDF 被重新导出过（字节变了 → hash 对不上），用 `title + totalPages` 二次匹配。

### F. 其余已知风险

| 风险 | 对策 |
|---|---|
| 189MB 大书 | `/file` 路由必须支持 HTTP Range；首屏先渲封面 + 前 3 页 |
| iPad / 移动端内存 | 页面渲染结果 LRU 缓存 + 及时 `page.cleanup()`，否则翻几十页内存持续涨 |
| 远程资源服务器 | 若 PDF 走远程（Caddyfile 已代理 `/data`、`/lt`），前端 fetch 需配 CORS |
| 双份数据心智负担 | 导航上明确区分「图书」与「PDF 书库」两个入口，不做数据互通 |
